# Схема базы данных

Информационная модель раздела 6 технического задания версии 1.0 от 06.10.2026.
Файлы миграций — `backend/migrations/001_initial.sql`.

---

## 1. Общие правила

| Правило | Реализация |
|---|---|
| Внутренний идентификатор | UUID (`TEXT PRIMARY KEY`) для каждого объекта — п.6.1 п.1 |
| Читаемый номер проекта | `code` вида `РНП-2026-0001`, `UNIQUE`, не переиспользуется — FR-06 |
| Связи | Внешние ключи с `ON DELETE` — удаление каскадное там, где объект не имеет собственной истории, и `SET NULL` там, где связь не должна уничтожать запись |
| Архивирование | Вместо удаления — поле `archived_at` — п.6.1 п.5, FR-31 |
| Журнал | `audit_events` — только вставка, операций правки и удаления нет |
| Справочники | `dict_items` — правятся без изменения кода — FR-30 |
| Настройки | `settings` — пороговые сроки, шаблоны номеров — FR-35 |

Схема снабжена проверками целостности (`CHECK`) для перечислений: статусы,
маршруты, индикаторы риска, режимы публикации, стадии результата и публикации,
признаки T-01…T-06. Ошибочное значение не попадёт в базу даже при обходе
приложения.

## 2. Сущности информационной модели

### Program — научная программа

`programs`, `program_curators`

Программа — временная общеуниверситетская рамка, объединяющая проекты по общей
проблематике. **Программа не является подразделением.** Паспорт содержит
критерии включения и ожидаемые результаты (M-01).

Куратор назначается на конкретную программу, а не получает глобальную роль:
один человек может курировать одну программу и быть участником проекта другой.

### Project — карточка проекта

`projects`, `project_full_route_reasons`, `project_partners`

Центральная сущность. 10 разделов карточки (раздел 6.2 ТЗ) хранятся в одной
таблице, потому что карточка — **одна** запись, дополняемая на протяжении
жизненного цикла: при смене стадии карточка не создаётся заново
(принцип «один проект — одна карточка»).

| Группа столбцов | Раздел карточки | Примеры |
|---|---|---|
| `code`, `title`, `short_title`, `public_annotation`, `program_id`, `theme_link`, `route`, `status`, `risk_level`, `planned_*`, `leader_person_id`, `publish_mode` | 1. Паспорт | A-01…A-16 |
| `problem`, `question`, `goal`, `tasks`, `research_object`, `research_subject`, `methods`, `data_basis`, `planned_result_type`, `result_criteria`, `novelty`, `applicability`, `limitations`, `*_data`, `*_subjects`, `legal_basis_*`, `confidentiality`, `ip_note`, `resource_request` | 2. Научное содержание | A-17…A-34 |
| `flag_*` (11 признаков) | Признаки маршрута | T-01…T-06 |

`version` обеспечивает контроль версии при параллельном редактировании
(FR-32): клиент передаёт версию, которую открыл; при расхождении запись
отклоняется с кодом 409, и незаметная перезапись невозможна.

`search_blob` — подготовленный текст для поиска (FR-25): собирается при
изменении карточки, поэтому поиск не просматривает десятки столбцов построчно.

### Person — профиль человека

`persons`, связана с `users.person_id`

**Один человек — один профиль** (FR-03). Профиль используется во всех проектах
и результатах. Основной ключ сопоставления при импорте — служебный адрес или
учётная запись (п.6.1 п.2): повторный ввод не создаёт дубль.

Хранится ровно то, что нужно для управления проектом: Ф. И. О., место работы
или обучения, должность, учёная степень, служебный контакт, категория
(п.11.2 п.3). **Первичные необезличенные массивы данных респондентов,
пациентов и иных исследуемых лиц не хранятся** (п.11.2 п.1).

Профиль архивируется, а не удаляется: блокировка учётной записи не должна терять
историю (ПС-22).

### Participation — участие в проекте

`participations`

Связь многие ко многим между людьми и проектами: роль (`leader`, `member`,
`supervisor`, `curator`), задача, период участия, доля вклада, признак
подтверждения вклада и признак разрешения к публикации.

Руководитель — это одновременно `projects.leader_person_id` и запись участия с
ролью `leader`. Дублирование намеренное: первое — быстрый доступ к руководителю
в фильтрах, второе — участие с задачей и периодом. Смена руководителя обновляет
обе записи в одной транзакции.

### Milestone — контрольная точка

`milestones`, `milestone_postponements`

Плановая и фактическая дата, ответственный, плановое подтверждение, статус,
подтверждение выполнения, причина переноса (A-35…A-42).

Просрочка рассчитывается автоматически (FR-13) и переводит статус точки в
`overdue`. Отдельная таблица `milestone_postponements` хранит историю переносов:
прежняя дата, новая дата, причина, кто и когда (FR-12).

### Risk — риск

`risks`

Категория, описание, вероятность, влияние, меры, владелец, срок проверки,
статус, уровень и комментарий к уровню (A-65).

**Ручное изменение уровня требует комментария** — иначе можно было бы тихо
снизить красный риск до зелёного.

### Review — экспертное заключение

`reviews`

Объект экспертизы (`project` или `result`), вид, эксперт, признак подтверждения
отсутствия конфликта интересов, четыре обязательных блока заключения,
рекомендация, срок, дата фиксации, версия (A-63, п.7.1).

| Механизм | Назначение |
|---|---|
| `finalized_at` | После фиксации заключение **не редактируется** |
| `version_no` | Исправление оформляется новой версией, исходная сохраняется |
| `replaced_by_review_id` | Связь с новой версией |
| `recused_at`, `recused_by`, `conflict_note` | Самоотвод фиксируется безвозвратно (п.4.1 п.6) |
| `expert_declared_no_conflict` | Подтверждение отсутствия конфликта (п.4.1 п.4) |

### Decision — решение

`decisions`

Объект, уровень (`curator`, `prorector`, `rector`, `council`, `secretary`), вид,
формулировка, **основание**, условия, ответственный, срок исполнения, отметка об
исполнении (A-64).

Основание — `NOT NULL`: решение без основания физически не создаётся.

### Result — результат

`results`, `result_projects`

Самостоятельная подтверждаемая запись (FR-16). Многие ко многим с проектами
через `result_projects`.

**Один результат может быть связан с несколькими проектами, но учитывается в
общей статистике один раз** (FR-17, п.6.1 п.3, сценарий ПС-12). Счёт
результатов ведётся по таблице `results`, а не по числу связей: связь с двумя
проектами не превращает одну работу в две.

`doi`, `edn`, `url` — для проверки дубля по п.6.1 п.4.

### Publication — публикация

`publications`

Расширение результата типа «публикация»: вид, стадия, целевое издание, даты
подачи, принятия и публикации, выходные данные, внутреннее рецензирование
(A-55…A-62).

**Стадии раздельные** (FR-18): замысел, внутренняя экспертиза, подана, доработка,
принята, опубликована. Переход вперёд требует заполнения полей, положенных по
стадии; переход назад запрещён для опубликованных записей.

### Dissertation — диссертация

`dissertations`, `dissertation_projects`, `dissertation_stages`

Аспирант, тема, специальность, научный руководитель, год защиты, статус;
связи с проектами и этапы работы (FR-19, A-67). Одна запись на одну диссертацию.

### StudentTask — задача обучающегося

`student_tasks`

Проект, диссертация, задание, исполнитель, руководитель, сроки, плановый и
фактический результат, признак публикации (FR-20, A-66).

Одна запись на одну задачу — повторная регистрация отклоняется. Продолжительность
**проверяется: от 6 до 16 недель**.

### Evidence — материал

`evidences`

Связанный объект, название, тип (`link` или `file`), URL или путь к файлу,
версия, контрольная сумма, размер, уровень доступа (`internal`, `restricted`,
`public`).

Один материал может использоваться несколькими объектами. В MVP хранятся
ссылки; защищённые вложения и версии — вторая очередь (FR-21).

`access_level` существует не для украшения: файлы **не отдаются напрямую из
файловой системы**. Выдача идёт только через приложение с проверкой прав, иначе
уровень доступа в таблице не имел бы смысла (SEC-02).

### AuditEvent — событие аудита

`audit_events`

Время, пользователь, группа событий, объект, действие, прежнее и новое значение,
основание, результат операции (`ok`, `denied`, `error`), адрес (A-69).

Неизменяемая запись. В API **нет** операций обновления и удаления журнала.
Отказы фиксируются с причиной — это основной источник для разбора вопроса
«почему система не дала сменить статус».

Индексы: объект, время, пользователь.

## 5. Правила недублирования (п.6.1)

| № | Правило | Реализация |
|---|---|---|
| 1 | UUID + неизменяемый номер | `id TEXT PRIMARY KEY`, `code TEXT UNIQUE`, номера не переиспользуются |
| 2 | Один человек — один профиль; ключ сопоставления — учётная запись или служебный адрес | Уникальность `users.email`, `persons.service_contact`; `create_person` возвращает существующий профиль вместо дубля |
| 3 | Один результат — много проектов, учёт один раз | `result_projects` (PK из двух столбцов), счёт по `results` |
| 4 | Проверка дубля публикации по DOI, EDN либо названию, авторам и году | `check_result_duplicates` + индексы на `doi`, `edn` |
| 5 | Использованные записи не удаляются, а архивируются | `archived_at` во всех основных таблицах. Физическое удаление из интерфейса запрещено (п.10.1 п.3) |
| 6 | Публичная карточка — не отдельная сущность | `services/public.py` формирует её из разрешённых полей внутренней записи |

## 7. Работа с соединением

| Параметр | Значение | Зачем |
|---|---|---|
| `journal_mode` | WAL | Читатели не мешают писателю — основа NFR-01 при 50 пользователях |
| `synchronous` | NORMAL | Баланс надёжности и скорости; ежедневное резервное копирование покрывает риск потери |
| `foreign_keys` | ON | Ссылочная целостность на самом сервере |
| `busy_timeout` | из настройки (30 с) | Ожидание освобождения блокировки вместо немедленной ошибки |
| Соединение | **по одному на поток** (`threading.local`) | FastAPI исполняет синхронные обработчики в пуле потоков; одно соединение на процесс падает с ошибкой «objects created in a thread can only be used in that same thread» |
| Транзакции | `BEGIN IMMEDIATE` для операций записи | Ошибка одной операции не повреждает данные других проектов (п.10.1 п.1) |

Последняя строка важна и неочевидна: ошибка «соединение должно работать в своём
потоке» не воспроизводится при последовательной проверке через `TestClient` и
проявляется только под конкурентной нагрузкой. Поэтому в наборе тестов есть
отдельная проверка параллельной работы.

## 8. Ёмкость

Расчётная ёмкость по NFR-05: до 2 000 пользователей, 10 000 проектов и
100 000 связанных записей без смены архитектуры.

При текущей схеме основной объём приходится на `audit_events`, который растёт
неизбежно: это цена требования «прозрачной истории». Для объёма ТЗ
(100 000 связанных записей) это порядка сотен тысяч строк журнала — с учётом
индексов единицы гигабайт. Если история станет расти быстрее, выносите
`audit_events` в отдельное хранилище; остальная схема при этом не меняется.

Фактические показатели измерены на пилотном наборе — в
[ПРОТОКОЛ-ИСПЫТАНИЙ.md](ПРОТОКОЛ-ИСПЫТАНИЙ.md).

## 9. Миграции

Файлы в `backend/migrations/` применяются в порядке имени при старте
приложения и отмечаются в таблице `schema_migrations`.

```bash
# применить (обычно автоматически при запуске)
.venv/bin/python -c "import sys; sys.path.insert(0,'backend'); \
  from app.db import run_migrations; print(run_migrations())"

# откат: удалить применённую запись из schema_migrations и выполнить
# обратный SQL вручную в отдельном окне
```

Приложение не удаляет и не меняет структуру автоматически: изменение схемы
требует контрольной копии и проверки на копии (п.11.4).
