# Инструкция по установке, обновлению, резервному копированию и восстановлению

## 1. Программные компоненты

### Обязательные

| Компонент | Версия | Назначение |
|---|---|---|
| Python | 3.11 и выше | Сервер приложения. Проверено на 3.12 и 3.14 |
| SQLite | 3.35 и выше | Реляционная база данных. Требуется поддержка режима WAL |
| Node.js | 20 и выше | Только на этапе сборки интерфейса |
| nginx | 1.18 и выше | HTTPS, раздача интерфейса, ограничение частоты запросов |
| Linux | любой поддерживаемый с Python 3.11 | Сервер приложения под управлением systemd |
| Windows | 10/11, Server 2019+ | Разработка и приёмка |

### Python-библиотеки

`backend/requirements.txt`:

| Пакет | Зачем |
|---|---|
| `fastapi` | Сервер приложения |
| `uvicorn[standard]` | ASGI-сервер |
| `pydantic` | Проверка входных данных |
| `python-multipart` | **Обязателен.** Без него FastAPI не поднимает ни один маршрут с загрузкой файла — приложение не стартует |
| `openpyxl` | Импорт и выгрузка XLSX (FR-28, FR-29) |
| `tzdata` | **Обязателен.** На Windows нет системной базы часовых поясов; без него Python не знает `Europe/Moscow` и не стартует |
| `pytest`, `httpx` | Автотесты |

## 2. Установка на сервере

### 2.1. Подготовка системы

```bash
sudo useradd --system --home /opt/registry --shell /usr/sbin/nologin registry
sudo mkdir -p /opt/registry
sudo apt-get update && sudo apt-get install -y python3 python3-venv nginx sqlite3
```

### 2.2. Размещение кода

```bash
sudo git clone https://github.com/Eagle1man/reestr-nauchnyh-proektov.git /opt/registry
sudo chown -R registry:registry /opt/registry
cd /opt/registry
```

Исходный код находится под контролем университета (п.3.2 п.5, п.15 п.2).

### 2.3. Виртуальное окружение и зависимости

```bash
sudo -u registry python3 -m venv .venv
sudo -u registry .venv/bin/pip install --upgrade pip
sudo -u registry .venv/bin/pip install -r backend/requirements.txt
```

### 2.4. Файл конфигурации

```bash
sudo -u registry cp .env.example .env
sudo -u registry chmod 600 .env
```

Обязательно задать:

```bash
SECRET_KEY=$(.venv/bin/python -c "import secrets; print(secrets.token_urlsafe(48))")
sudo -u registry sed -i "s|^SECRET_KEY=.*|SECRET_KEY=$SECRET_KEY|" .env
```

Проверить:

```bash
sudo -u registry .venv/bin/python -c "
import sys; sys.path.insert(0,'backend')
from app.config import settings
print('SECRET_KEY задан:', bool(settings.secret_key) and len(settings.secret_key) >= 32)
print('База:', settings.db_file)"
```

Без `SECRET_KEY` приложение **не стартует**, а не работает с временным ключом:
незаметная подмена ключа сделала бы все ранее выданные сессии бессрочными.

### 2.5. Инициализация базы и наполнение

```bash
# Справочники, настройки, научные программы — обязательны
sudo -u registry .venv/bin/python backend/scripts/seed.py

# Учётные записи пилотного набора (с ролями ТЗ п.4)
sudo -u registry env SEED_PASSWORD='<временный пароль>' \
  .venv/bin/python backend/scripts/seed.py --with-users
```

Пароль выдаётся отдельно, по защищённому каналу (п.15 п.11). Учётные записи
создаются с признаком «требуется смена пароля».

### 2.6. Сборка интерфейса

```bash
cd frontend
sudo -u registry npm ci
sudo -u registry npm run build
cd ..
```

Сборка кладёт файлы в `frontend/dist`. Приложение раздаёт их само, отдельный
веб-сервер для статики не нужен.

### 2.7. Служба

```bash
sudo cp deploy/systemd/registry.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now registry
sudo systemctl status registry
```

Проверка:

```bash
curl -fsS http://127.0.0.1:8000/api/health
```

### 2.8. HTTPS

```bash
# Получить сертификат
sudo certbot certonly --nginx -d science.iubip.ru

# Установить конфигурацию
sudo cp deploy/nginx/registry.conf /etc/nginx/sites-available/
sudo cp deploy/nginx/proxy-common.conf /etc/nginx/snippets/
sudo ln -s /etc/nginx/sites-available/registry.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

Проверка перенаправления:

```bash
curl -I http://science.iubip.ru/          # 301 на https
curl -I https://science.iubip.ru/         # 200
```

### 2.9. Запись DNS

Тип A на `science.iubip.ru` → адрес сервера. Зависит от того, кто ведёт домен
(вопрос 2 ТЗ на согласовании).

### 2.10. Резервное копирование по расписанию

```bash
sudo cp deploy/systemd/registry-backup.{service,timer} /etc/systemd/system/
sudo cp deploy/systemd/registry-backup-weekly.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now registry-backup.timer registry-backup-weekly.timer
sudo systemctl list-timers 'registry-*'
```

## 3. Установка в контейнере

```bash
cp .env.example .env   # заполнить SECRET_KEY
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml exec registry \
  python backend/scripts/seed.py --with-users

# Разовая копия
docker compose -f deploy/docker-compose.yml run --rm backup
```

Приложение в контейнере наружу не публикуется: доступ только через обратный
прокси. Тома `registry-data` и `registry-backups` разделены намеренно —
потеря тома с данными не должна уничтожать копии.

## 4. Обновление

### 4.1. Порядок

Контрольная копия перед обновлением обязательна (п.11.4).

```bash
cd /opt/registry

# 1. Зафиксировать текущее состояние
VERSION=$(git rev-parse --short HEAD)
echo "Текущая версия: $VERSION"

# 2. Контрольная копия
sudo -u registry .venv/bin/python backend/scripts/backup.py --before-update "$VERSION"

# 3. Обновить код
sudo -u registry git pull

# 4. Установить зависимости, если изменились
sudo -u registry .venv/bin/pip install -r backend/requirements.txt

# 5. Пересобрать интерфейс
cd frontend && sudo -u registry npm ci && sudo -u registry npm run build && cd ..

# 6. Применить миграции — происходит автоматически при старте,
#    но лучше увидеть результат явно:
sudo -u registry .venv/bin/python -c \
  "import sys; sys.path.insert(0,'backend'); \
   from app.db import run_migrations; print('миграции:', run_migrations())"

# 7. Перезапустить
sudo systemctl restart registry

# 8. Проверить
curl -fsS https://science.iubip.ru/api/health
sudo -u registry .venv/bin/python backend/scripts/smoke.py https://science.iubip.ru '<ПАРОЛЬ>'
```

### 4.2. Откат

```bash
cd /opt/registry
sudo -u registry git checkout <предыдущий-коммит>

sudo -u registry .venv/bin/python backend/scripts/backup.py \
  --restore /opt/registry/backups/registry-before-update-*.sqlite3 --confirm

sudo systemctl restart registry
curl -fsS https://science.iubip.ru/api/health
```

Скрипт восстановления **сам** создаёт копию текущего состояния перед
восстановлением, поэтому откат не уничтожит изменения, сделанные после последней
копии.

## 5. Резервное копирование

### 5.1. Требования ТЗ

| Параметр | Требование | Как обеспечено |
|---|---|---|
| Периодичность | Не реже раза в сутки | `registry-backup.timer`, ежедневно 03:17 |
| Состав | БД, конфигурация, файловое хранилище | Копия БД + копия `.env` рядом с ней |
| Хранение | Ежедневные ≥ 30 дней; недельная отдельно | `--purge` с сохранением недельных; отдельный таймер |
| Перед обновлением | Обязательная копия | `--before-update` |
| RPO | ≤ 24 часов | Ежедневный таймер |
| RTO | ≤ 8 рабочих часов | Восстановление копии — минуты |
| Проверка | До приёмки и раз в квартал | Контрольное восстановление |

### 5.2. Почему копия делается не копированием файла

Система использует механизм резервного копирования SQLite, а не `cp`.

При включённом журналировании (WAL) последние изменения лежат в файле журнала,
а не в основном файле базы. Копирование файла `.db` даёт снимок, который
**открывается и выглядит рабочим, но не содержит последних изменений**. Такая
копия обнаруживается только при аварийном восстановлении — когда она уже не
помогает.

### 5.3. Почему проверка смотрит содержимое

Проверка копии не ограничивается фактом открытия файла: обрезанный файл тоже
открывается. Проверяются:

1. целостность по `PRAGMA integrity_check`;
2. наличие всех ожидаемых таблиц;
3. **читаемость данных** в ключевых таблицах;
4. число проектов в копии против числа проектов в рабочей базе — так отвергается
   снимок, сделанный не из той базы.

### 5.4. Команды

```bash
# Ежедневная копия, если сегодня ещё нет
.venv/bin/python backend/scripts/backup.py

# Принудительно создать ещё одну
.venv/bin/python -c "
import sys; sys.path.insert(0,'backend')
from app.backup import create_backup; print(create_backup())"

# Еженедельная копия для отдельного хранилища
.venv/bin/python backend/scripts/backup.py --weekly

# Список с возрастом и состоянием срока хранения
.venv/bin/python backend/scripts/backup.py --list

# Проверка копии
.venv/bin/python backend/scripts/backup.py --verify <путь>

# Удалить устаревшие (недельные и предрелизные сохраняются)
.venv/bin/python backend/scripts/backup.py --purge
```

Из интерфейса: «Администрирование» → «Резервное копирование».

### 5.5. Хранение вне сервера

Еженедельную копию нужно выносить за пределы сервера. Потеря сервера не должна
уничтожать все копии.

```bash
# После снятия недельной копии
rsync -a /opt/registry/backups/registry-weekly-*.sqlite3 \
      /mnt/registry-offsite/registry/
```

Носитель и каталог назначения согласуются с владельцем инфраструктуры.

## 6. Восстановление

### 6.1. Контрольное восстановление

Выполняется до приёмки и далее не реже одного раза в квартал.

```bash
# 1. Выбрать копию (еженедельная лежит отдельно и переживёт потерю сервера)
ls -lt /opt/registry/backups/registry-weekly-*.sqlite3

# 2. Проверить БЕЗ применения
.venv/bin/python backend/scripts/backup.py --verify <путь>

# 3. Восстановить (текущее состояние сохраняется автоматически)
sudo systemctl stop registry
.venv/bin/python backend/scripts/backup.py --restore <путь> --confirm
sudo systemctl start registry

# 4. Проверить содержимое, а не код завершения
curl -fsS https://science.iubip.ru/api/health
```

### 6.2. Что проверять после восстановления

| Что | Как |
|---|---|
| Карточки открываются | Панель → число проектов совпадает с исходной базой |
| Связи целы | Открыть проект: команда, точки, результаты на месте |
| Статусы и маршруты | Список проектов: фильтр по статусу и маршруту работает |
| Журнал действий | «Журнал» → события присутствуют и читаются |
| Публичный контур | `/api/public/v1/projects` отдаёт ожидаемое число записей |
| Целостность | `sqlite3 /opt/registry/backend/data/registry.db "PRAGMA integrity_check;"` |

**Успешный код возврата при неполной копии — именно тот случай, когда
восстановление считают удачным, а данные теряют.** Проверка содержимого
обязательна.

Результат заносится в [ПРОТОКОЛ-ИСПЫТАНИЙ.md](ПРОТОКОЛ-ИСПЫТАНИЙ.md).

### 6.3. Аварийное восстановление

Полный сервер утрачен:

1. Развернуть новый сервер по разделу 2.
2. Установить ту же версию кода, что была до сбоя.
3. Скопировать `.env` (в нём `SECRET_KEY`: смена ключа завершит все сессии).
4. Скопировать последнюю недельную копию из отдельного хранилища.
5. Восстановить по разделу 6.1.
6. Проверить по разделу 6.2.
7. Пересчитать индикаторы риска: «Администрирование» → «Обслуживание».

Целевой срок: RTO — не более 8 рабочих часов.

## 8. Передача административных доступов

По п.15 п.11 доступы передаются **отдельно от документации**, по защищённому
каналу.

Что передаётся:

| Что | Кому | Как |
|---|---|---|
| `SECRET_KEY` | Владелец сервера | Защищённый канал, не в почте обычной |
| Учётная запись `sysadmin` и её начальный пароль | Назначенный технический администратор | Защищённый канал; пароль показывается один раз |
| Доступ к серверу (SSH-ключ, ограниченный набор команд) | Владелец инфраструктуры | Защищённый канал |
| Учётные записи по ролям ТЗ п.4 | Секретарь, проректор, кураторы | С выдачей пароля при первом входе |

Пароли **не указываются** в этом документе, в репозитории и в переписке.
Восстановление доступа выполняет администратор либо подтверждённый служебный
адрес (п.11.1 п.4).

Перед передачей смените `SECRET_KEY`, если использовались тестовые значения:
смена ключа завершит все текущие сессии.
