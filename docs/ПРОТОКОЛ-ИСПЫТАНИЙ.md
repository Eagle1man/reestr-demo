ПС-01, ПС-04, ПС-09, ПС-13, ПС-17, ПС-18, ПС-22 — автоматически в
`backend/scripts/smoke.py` и `backend/tests`.

Остальные — прохождением полного цикла на пилотных проектах с фиксацией в
журнале действий: журнал и есть доказательство (п.14.4 п.4, отдельные

### Замечание к ПС-21

пикселей. Проверка в конкретных версиях Safari на физических устройствах Apple
не проводилась: оборудование не предоставлено. Требуется проверка перед
приёмкой — это обычное замечание, а не дефект.

## 8. Обнаруженные дефекты и их устранение

Все дефекты, найденные автоматическими проверками, устранены до передачи.

| Дефект | Причина | Устранение |
|---|---|---|
| Пустая база данных при запуске не из корня | Процесс создавал БД относительно текущего каталога | Путь к базе выводится при старте; проверка перед стартом службы |
| Ошибка SQL в видимости портфеля | Несуществующий алиас таблицы `pc2` | Алиас приведён в соответствие |
| Ошибка SQL в публичной команде | Обращение к полю таблицы участия вместо профиля | Поля `position`, `work_place` берутся из `persons` |
| Ошибка SQL в выборке контрольных точек | Неоднозначное имя `archived_at` при соединении с `persons` | Имя уточнено префиксом таблицы |
| Список материалов не открывался | Обращение к несуществующему полю `created_at` | Правильное имя поля `uploaded_at` |
| Агрегаты панели не работали | Таблица без аликса при префиксованном условии | Алиас добавлен |
| Ответ 429 не содержал заголовков лимита | Заголовки добавлялись только при успешной выдаче | Заголовки добавляются и при отказе |
| Сценарий нагрузки давал ложные отказы | Измерял публичный API, а NFR-01 — об авторизованных пользователях | Сценарий разделён: NFR-01 — авторизованные, лимит проверяется отдельно |
| Демонстрационные проекты не получали полный маршрут | Признаки T-01…T-06 передавались вложенным объектом | Признаки передаются плоскими полями |
| Все проекты получали красный риск | У всех была просроченная контрольная точка | Просрочка назначается только проекту по составу Приложения Г |

Дефекты, выявленные регрессионным набором (389 проверок) и устранённые до передачи:

| Дефект | Причина | Устранение |
|---|---|---|
| **Критический:** проект не мог выйти из «Черновика» | Проверка комплектности получала только редактируемые поля, а программа (A-05) и руководитель (A-12) задаются при создании — они всегда считались незаполненными (FR-07, FR-10) | Проверка берёт все поля строки (`completeness_source`) |
| Параллельное создание давало 500 | Номер РНП считался SELECT-ом вне транзакции: 28 карточек из 50 получали одинаковый номер и падали по UNIQUE (FR-06, NFR-01) | Генерация номера и вставка внутри одной транзакции с повтором |
| Любая правка контрольной точки падала 500 | В SQL передавалась пара «прежнее, новое» вместо значения | В запрос идёт только новое значение (FR-12) |
| Один результат на два проекта учитывался дважды | `COUNT(*)` по JOIN вместо `COUNT(DISTINCT r.id)` (FR-17, ПС-12) | Счётчик уникальных идентификаторов |
| Публичная карточка раскрывала маршрут | Поле `route` помечено в Приложении А как «Открыто: Нет» (SEC-03) | Поле исключено из публичной проекции |
| Поиск по русским словам ничего не находил | SQL `lower()` в SQLite работает только с ASCII | Поиск по `search_blob`, приведённому к нижнему регистру при записи (FR-25, п.9.4) |
| Уборка удаляла недельные и контрольные копии | Признак искался как «-weekly-» в середине имени, а файлы начинаются с «weekly-» (п.11.4) | Сравнение по префиксу имени |

## 12. Процедура приёмки

По п.14.4:

1. Разработчик проводит внутреннее тестирование и передаёт заполненный перечень
   сценариев — настоящий документ.
2. Совместная проверка проводится в одной рабочей сессии продолжительностью
   **до 90 минут**.
3. Участвуют: проректор по науке, функциональный администратор, один куратор,
   один руководитель проекта, разработчик.
4. Доказательства — записи реестра, журнал действий, выгрузки и краткий протокол.
   Отдельные развёрнутые отчёты не требуются.
5. Замечания ведутся в одном перечне с уровнем, ответственным и сроком.
6. После исправления повторно проверяются **только затронутые и связанные
   функции**.

### Уровни замечаний (п.14.3)

| Уровень | Описание | Решение |
|---|---|---|
| Критическое | Недоступность системы, потеря данных, обход прав доступа, невозможность выполнить основной цикл | Блокирует приёмку |
| Высокое | Неработоспособность ключевой функции без приемлемого обходного решения | Блокирует приёмку MVP |
| Обычное | Частичная ошибка при наличии безопасного обходного способа | Включается в срок исправления |
| Улучшение | Изменение удобства или новая функция | Включается в план развития |
