# Руководство технического администратора

Для администратора, обслуживающего установку реестра научных проектов.
Установка и обновление описаны отдельно в
[ИНСТРУКЦИЯ-РАЗВЁРТЫВАНИЯ.md](ИНСТРУКЦИЯ-РАЗВЁРТЫВАНИЯ.md).

**Технический администратор не принимает научных решений.** Он отвечает за
учётные записи, конфигурацию, резервное копирование, обновления, интеграции и
технический аудит.

---

## 1. Учётные записи

### Создание

Раздел «Администрирование» → «Учётные записи».

Пароль выдаётся один раз и в журнал не записывается. Передайте его
пользователю по защищённому каналу. Учётная запись создаётся с признаком
«требуется смена пароля».

Требования к паролю (п.11.1): не менее 12 символов, строчные и прописные буквы,
цифры, специальные символы. Если вы задаёте пароль вручную и он не соответствует
требованиям, система его не примет.

### Роли

Роли выдаются здесь, кроме куратора программы: куратор назначается на конкретную
программу, а не на учётную запись.

| Роль | Кому |
|---|---|
| `sysadmin` | Системный администратор (внутрисистемная роль) |
| `techadmin` | Технический администратор |
| `rector` | Ректор |
| `council` | Научный совет |
| `prorector` | Проректор по науке |
| `secretary` | Секретарь Научного совета |

Роли **руководителя проекта, участника и эксперта** здесь не выдаются: это
отношение к конкретному проекту, оно возникает автоматически при назначении
руководителя, добавлении в команду или назначении экспертизы.

### Сброс пароля

Кнопка «Сбросить пароль» выпускает новый пароль и закрывает все сессии
пользователя. Новый пароль показывается один раз.

### Блокировка

Кнопка «Отключить» прекращает доступ и закрывает сессии. **Внесённые данные,
профили и история сохраняются** — это требование сценария ПС-22 ТЗ.

Если человек уволен или утратил доступ, отключите учётную запись, но не удаляйте
её: связанные с ней карточки, экспертизы и решения должны остаться
прослеживаемыми.

### Общие учётные записи

Создание учётной записи «Научный совет», «Секретарь» или иной общей записи
**запрещено** п.4.1 ТЗ. Общая запись делает журнал действий бессмысленным:
невозможно установить, кто именно принял решение.

## 2. Справочники

Раздел «Администрирование» → «Справочники».

Перечни меняются без правки кода (FR-35). Справочники:

| Ключ | Справочник |
|---|---|
| `method` | Методы исследования |
| `result_type` | Виды результатов |
| `risk_category` |Категории рисков |
| `organization` | Организации |
| `publication_kind` | Виды публикаций |
| `target_journal` | Целевые издания |
| `party_type` | Типы партнёров |

Запись отключается, а не удаляется: иначе карточки, ссылающиеся на неё, стали бы
нечитаемыми.

**Осторожно с `result_type`.** Код вида результата участвует в публичной выдаче и
в проверке готовности. Не удаляйте коды, которые уже используются в результатах.

## 3. Настройки

Раздел «Администрирование» → «Настройки».

Пороговые сроки и перечни меняются здесь (FR-35):

| Ключ | Смысл | По умолчанию |
|---|---|---|
| `project_code_prefix` | Префикс номера проекта | `РНП` |
| `result_code_prefix` | Префикс номера результата | `РЕЗ` |
| `yellow_delay_working_days` | Порог жёлтого индикатора | 20 |
| `completeness_check_days` | Срок проверки комплектности | 3 |
| `expert_review_days` | Срок экспертизы | 10 |
| `decision_days` | Срок решения после заключения | 5 |
| `student_task_min_weeks` | Минимальная длительность задачи обучающегося | 6 |
| `student_task_max_weeks` | Максимальная длительность задачи | 16 |
| `public_cache_seconds` | Время кеширования публичного API | 300 |
| `retention_content_years` | Срок хранения содержательной истории | 5 |
| `retention_technical_months` | Срок хранения технических журналов | 12 |

Каждое изменение фиксируется в журнале с указанием прежнего и нового значения.

## 4. Резервное копирование

### Требования ТЗ (п.11.4)

| Параметр | Требование |
|---|---|
| Периодичность | Не реже одного раза в сутки |
| Состав | База данных, конфигурация и файловое хранилище при наличии |
| Хранение | Ежедневные копии не менее 30 календарных дней; еженедельная — отдельно |
| Перед обновлением | Обязательная контрольная копия |
| RPO | Не более 24 часов |
| RTO | Не более 8 рабочих часов |
| Проверка | Контрольное восстановление до приёмки и далее раз в квартал |

### Почему копия делается особым способом

Система **не копирует файл базы**. Она использует механизм резервного копирования
SQLite, который снимает согласованный снимок.

Причина: база работает в режиме журналирования (WAL), и последние изменения
хранятся не в основном файле, а в файле журнала. Обычное копирование файла
`.db` даёт снимок, **который выглядит рабочим, но не содержит последних
изменений**. Обнаружится это только в момент аварийного восстановления — то
есть тогда, когда восстановление уже не помогает.

### Почему проверка смотрит содержимое

Проверка копии не ограничивается фактом «файл открылся». Обрезанный файл тоже
открывается. Проверка сравнивает:

- целостность по `PRAGMA integrity_check`;
- наличие всех ожидаемых таблиц;
- читаемость данных в ключевых таблицах;
- число проектов в копии с числом проектов в рабочей базе.

Снимок, сделанный не из той базы или обрезанный, будет отвергнут.

### Расписание

systemd-таймеры в комплекте:

```
registry-backup.timer          ежедневно в 03:17
registry-backup-weekly.timer   воскресенье в 04:23
```

Проверка состояния:

```bash
systemctl list-timers 'registry-*'
journalctl -u registry-backup --since '7 days ago'
```

### Ручные операции

```bash
# Ежедневная копия, если сегодня ещё не создана
.venv/bin/python backend/scripts/backup.py

# Еженедельная копия для отдельного хранилища
.venv/bin/python backend/scripts/backup.py --weekly

# Список копий с указанием возраста и состояния срока хранения
.venv/bin/python backend/scripts/backup.py --list

# Проверка копии без применения
.venv/bin/python backend/scripts/backup.py --verify /opt/registry/backups/registry-20261008-031700.sqlite3

# Удалить копии старше срока хранения (недельные и предрелизные сохраняются)
.venv/bin/python backend/scripts/backup.py --purge
```

### Контрольное восстановление

Выполняется до приёмки и далее не реже одного раза в квартал.

1. Выберите последнюю еженедельную копию — она лежит отдельно и переживёт потерю
   сервера.
2. Создайте копию текущего состояния: `backup.py` делает это сам перед
   восстановлением.
3. Разверните копию в отдельный экземпляр приложения или восстановите на место.
4. Проверьте **содержимое**, а не код завершения:

```bash
.venv/bin/python backend/scripts/backup.py --restore <путь> --confirm
```

5. Проверьте вручную: карточки, связи, статусы и журнал действий открываются;
   число проектов и результатов совпадает с исходной базой.

**Успешный код возврата при неполной копии — ровно тот случай, когда
восстановление считают удачным, а данные теряют.** Поэтому проверка содержимого
обязательна, а формальна — нет.

### Обновление системы

```bash
cd /opt/registry
git pull
git log -1 --format=%h                      # версия
.venv/bin/python backend/scripts/backup.py --before-update "<версия>"
systemctl restart registry
# проверка
curl -fsS https://science.iubip.ru/api/health
```

Контрольная копия перед обновлением обязательна — п.11.4 не допускает
исключений. Если обновление прошло неудачно, восстановитесь:

```bash
.venv/bin/python backend/scripts/backup.py --restore \
  /opt/registry/backups/registry-before-update-*.sqlite3 --confirm
git checkout <предыдущий-коммит>
systemctl restart registry
```

## 5. Обслуживание

### Пересчёт индикаторов риска

«Администрирование» → «Обслуживание» → «Пересчитать индикаторы риска».

Индикаторы пересчитываются автоматически при любом изменении контрольных
точек. Ручной пересчёт нужен после массового импорта, восстановления из копии
или правки сроков напрямую.

### Сессии

«Обслуживание» → «Активные сессии». Сессия завершается сама через 60 минут
бездействия. Закрыть все сессии принудительно стоит только при подозрении на
компрометацию учётных записей.

### Служебные проверки

```bash
systemctl status registry
journalctl -u registry -f
journalctl -u registry --since '1 hour ago' -p err
curl -fsS https://science.iubip.ru/api/health
sqlite3 /opt/registry/backend/data/registry.db "PRAGMA integrity_check;"
```

## 6. Технический аудит

Журнал доступен в интерфейсе и содержит пять групп событий п.11.3:

| Группа | Что фиксируется |
|---|---|
| Вход и безопасность | Успешные и неудачные входы, блокировка, изменение ролей и прав, сброс пароля |
| Карточка | Создание, архивирование, смена маршрута, статуса, риска, руководителя, срока, цели, результата |
| Экспертиза и решение | Назначение, самоотвод, заключение, решение, изменение условий, исполнение |
| Публикация | Разрешение, передача, изменение, снятие публичных данных |
| Администрирование | Импорт, выгрузка, справочники, резервное копирование, восстановление, обновление |

Для каждого события хранятся дата и время, пользователь, объект, операция и
результат. История содержательных изменений хранится весь жизненный цикл проекта
и не менее пяти лет после его завершения; технические журналы — не менее 12
месяцев.

События отказов — основной источник для разбора «почему система не дала
выполнить действие». В отказе всегда указана причина.

## 7. Безопасность при эксплуатации

### Секреты

- `SECRET_KEY` живёт только в `.env`, файл в `.gitignore` и имеет права `0600`.
- Пароли не хранятся в открытом виде: PBKDF2-HMAC-SHA256, 260 000 итераций.
- Пароль показывается один раз — при создании учётной записи и при сбросе.
- В журналы попадает факт операции, а не её секретное содержимое.

При подозрении на компрометацию `SECRET_KEY` его нужно сменить. Учтите: смена
ключа завершит все сессии.

### Транспорт

Доступ только по HTTPS (SEC-01); HTTP перенаправляется на HTTPS. Сертификат
выпускается автоматически продлением certbot.

База данных и служебные интерфейсы наружу не публикуются: приложение слушает
только `127.0.0.1`, наружу — nginx.

### Ограничение частоты

| Маршрут | Ограничение | Назначение |
|---|---|---|
| `/api/public/` | 60 запросов в минуту с адреса | Защита публичного API (FR-33) |
| `/api/auth/login` | 10 запросов в минуту с адреса | Защита от подбора пароля (SEC-04) |

Отказ сопровождается кодом 429 и заголовком `Retry-After`. Причину отказа
пользователю объяснять не нужно: подробности помогают перебору.

### Блокировка входа

После пяти последовательных неудачных попыток вход в **учётную запись**
блокируется на 15 минут (п.11.1). Перебор с одного адреса ограничен отдельно
порогом в 25 неудачных попыток.

Это разделение сделано намеренно. Если бы блокировка срабатывала только по
логину, любой посторонний мог отправить пять неверных паролей от имени
сотрудника и лишить его доступа на 15 минут. Ограничение по адресу защищает от
перебора, не создавая этой проблемы.

### Ограничения файловой загрузки

Загрузка файлов не реализована (вторая очередь, ждёт решения по вопросу 10 ТЗ).
Ограничения `UPLOAD_MAX_BYTES` и `UPLOAD_ALLOWED_EXTENSIONS` заданы в `.env`
заранее — их значения нужно согласовать с владельцем сервера до включения
загрузки.

## 8. Типовые неисправности

| Симптом | Причина | Что делать |
|---|---|---|
| Приложение не стартует, в журнале ошибка про `SECRET_KEY` | Не задан или слишком короткий ключ | Задать `SECRET_KEY` в `.env`, минимум 32 знака |
| 423 при входе, хотя пароль верный | Сработала блокировка после неудачных попыток | Подождать 15 минут; проверить счётчик в разделе «Журнал» |
| 429 на публичный API | Исчерпан лимит запросов с адреса | Обычно признак интеграции, перебирающей данные; смотрите `X-RateLimit-Remaining` |
| 409 «Карточка изменена после вашего открытия» | Два пользователя редактируют карточку | Обновить страницу и внести правки заново |
| Публичный API отдаёт 404 для опубликованного проекта | Нет разрешения, статус не публикуемый или нет аннотации | Смотреть «Публичное представление» в карточке — система перечисляет причины |
| Выгрузка CSV содержит иероглифы | Файл открыт без учёта кодировки | В файле есть BOM; в Excel выбрать «Данные → из текстового файла → UTF-8» |
| Копия не прошла проверку | Копия пуста, обрезана или сделана не из той базы | Копия непригодна; создать заново, проверить место хранения |
| Импорт вернул ошибки по всем строкам | Файл не соответствует шаблону формы | Скачать шаблон заново и сверить заголовки колонок |

## 9. Проверка после любых работ

```bash
# 1. Служба жива
curl -fsS https://science.iubip.ru/api/health

# 2. Целостность базы
sqlite3 /opt/registry/backend/data/registry.db "PRAGMA integrity_check;"

# 3. Сквозная проверка (требует тестовой учётной записи)
.venv/bin/python backend/scripts/smoke.py https://science.iubip.ru <ПАРОЛЬ>

# 4. Копия актуальна и проходит проверку
.venv/bin/python backend/scripts/backup.py --list
.venv/bin/python backend/scripts/backup.py --verify <последняя копия>

# 5. Контрольное восстановление — раз в квартал
.venv/bin/python backend/scripts/backup.py --restore <еженедельная копия> --confirm
```

Результаты заносятся в [ПРОТОКОЛ-ИСПЫТАНИЙ.md](ПРОТОКОЛ-ИСПЫТАНИЙ.md).
